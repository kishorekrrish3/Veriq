How VERIQ Categorizes Proof: The Honest Status Model

VERIQ adheres to an honest, no-hallucination verification model: Passing syntax checks does not prove functional correctness. A retrieved document does not prove code runs. Real tests in a sandbox are required for proof.

VERIFIED REAL TESTS PASSED

An actual test suite executed in the isolated sandbox and exited with code 0 (all test assertions passed).

Evidence: Exit code 0, 0 stderr, all pytest test cases passed
SUPPORTED SYNTAX & DOCS CHECKED

Evidence supports the claim, but bounded by static analysis. Examples: Python AST parsed with zero syntax errors; Tavily found official library documentation.

Evidence: Official doc passage SHA-256 match, AST parse valid
FAILED CHECK OR TEST FAILED

A test or syntax check produced a failure. Examples: pytest assertion error, Python traceback, or illegal directory access. Triggers automatic self-repair!

Evidence: Exit code > 0, terminal traceback, assertion failure
UNRESOLVED INCONCLUSIVE

Evidence is missing or execution hit a limit. Examples: External service was unreachable or the test runner hit the 30-second hard timeout limit.

Evidence: Process timeout exceeded, incomplete coverage
NOT_RUN SKIPPED

The check was skipped intentionally (e.g. an earlier pipeline stage failed, or the user disabled that specific check).

Evidence: Check skipped in pipeline workflow graph
